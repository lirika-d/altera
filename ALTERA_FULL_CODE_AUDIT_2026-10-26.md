# ALTERA — полный аудит проекта

**Дата:** 26 октября 2026 г.  
**Режим:** read-only аудит; исходный код приложения, схема БД и реальные пользовательские данные не изменялись.  
**Проверенный снимок:** локальная рабочая копия ALTERA, ветка `main`; рабочее дерево уже содержало значительное количество пользовательских изменений до аудита.

## Краткий вывод

ALTERA уже имеет крепкую основу для локального приложения: TypeScript, разделение интерфейса и Dexie/IndexedDB persistence, транзакции для важных операций, миграции, проверка backup перед импортом, обработка восстановления и широкое модульное покрытие. Основные сквозные сценарии, которые удалось проверить в браузере, работают.

При этом «все функции полностью проверены» утверждать нельзя: тесты не покрывают каждый путь пользовательского интерфейса, браузерный прогон был выборочным, а производственная среда и реальные устройства недоступны. Самый серьёзный найденный риск — условная stored XSS через вредоносный импортированный backup с заметкой; также есть потенциальный main-thread stall на крупных backup. Это не было исправлено: запрос был на аудит.

## Архитектура: что хорошо

- React + TypeScript + Vite организованы как локально запускаемое SPA с маршрутами и ленивой загрузкой страниц. `src/App.tsx` выступает маршрутизатором/компоновщиком, отдельные страницы и компоненты содержат UI.
- Dexie/IndexedDB соответствует local-first модели: проекты, задачи, сессии, календарь и knowledge-данные не требуют обязательного серверного аккаунта. Изменения схемы проходят последовательными версиями в `src/db/db.ts`; текущая схема в проверенной копии — v9.
- Значимые операции со связями и удалением вынесены в persistence/service слой и используют транзакции, а не только последовательность независимых UI-обновлений. Это снижает риск частично изменённого графа данных.
- Для backup есть версионированный формат, лимит размера и строк, валидация связей до импорта, транзакционное применение и проверка целостности. Это хороший фундамент для восстановления данных.
- В проекте есть error boundary/диагностика восстановления, отдельная логика сессий, календаря, планировщика и аналитики; важные вычисления частично вынесены в чистые функции и тестируются отдельно.
- Автосохранение заметок имеет статус сохранения, revision-конфликты и локальные recoverable drafts. Ранее проведённые доработки отражены в текущем коде, однако этот аудит не является повторным нагрузочным аудитом всех сценариев записи.
- Автоматические тесты содержат реальные проверки БД, knowledge, backup, календаря, связей, routing, planner и локализации.

## Что стоит улучшить в архитектуре

1. **Чётче отделить домены данных.** `src/db/knowledge.ts` совмещает большой объём операций заметок, ресурсов, тегов и связей. В дальнейшем его можно разделить по доменам, сохранив общую транзакционную границу. Не делать это механическим рефакторингом в рамках исправления одной ошибки.
2. **Закрепить backup как отдельную границу доверия.** Проверять не только оболочку backup и типы полей, но и рекурсивную структуру rich-text документа, атрибуты ссылок и лимиты вложенности/объёма. Import UI не должен считать произвольный корректно распарсенный JSON безопасным содержимым.
3. **Сохранить local-first и явно документировать его последствия.** В этой архитектуре данные находятся в браузерном IndexedDB; синхронизации с сервером в просмотренном проекте нет. Потеря профиля браузера/устройства может означать потерю данных, поэтому регулярный экспорт и проверяемый сценарий восстановления — ключевая часть надёжности, а не дополнительная функция.
4. **Разделить чистую бизнес-логику и orchestration UI.** Чистые расчёты аналитики/календаря хорошо тестировать независимо; React-страницы стоит удерживать в роли композиции данных и пользовательских действий. Для больших компонентов пригодится постепенное выделение доменных UI-блоков, без переписывания всего приложения.
5. **Поддерживать размер и стоимость проверки backup.** Bundle check проходит текущий бюджет, однако начальная JS-загрузка составляет около 188 KB gzip, из них React vendor — около 67 KB gzip. Это пока не блокер, но стоит следить за графиком размера при добавлении фич.

## Находки и рекомендации

### P2 — Возможная stored XSS при импорте заметки

**Где:** `src/db/backupValidation.ts:28–35, 71–120`, `src/components/knowledge/editor/editorTypes.ts:93–100, 159–192`, `src/components/knowledge/editor/NoteEditor.tsx:149–152, 1276` (есть и другие аналогичные места рендеринга), `src/components/knowledge/notes/NoteDetail.tsx:716`, импорт в `src/pages/Settings.tsx:235–251`.

Валидация backup проверяет `contentJSON` заметки как строку, но не разбирает вложенные rich-text узлы/marks. `normalizeDoc` проверяет верхний уровень документа, а `sanitizeUrl` отклоняет несколько схем (`javascript:`, `data:`, `vbscript:`), но возвращает остальные строки без HTML attribute encoding. Затем `inlineContentToHTML` напрямую вставляет `href` в кавычки сырой строки `<a href="…">`, передаваемой в `dangerouslySetInnerHTML`.

**Условие эксплуатации:** пользователь должен выбрать и подтвердить специально подготовленный ALTERA v3 backup, затем открыть содержащую вредоносную ссылку заметку. Тогда URL с кавычкой может выйти из атрибута `href` и добавить обработчик события. Текст заметок экранируется, а подтверждение импорта есть — это снижает вероятность, но не устраняет риск. При выполнении скрипт действует в origin приложения и потенциально может читать/менять его IndexedDB.

**Рекомендация:** не импортировать backup от недоверенного источника до исправления. Структурно валидировать документ и marks, применять allowlist URL-схем, а ссылки отображать обычными React-атрибутами (`href` как значение prop), не интерполируя недоверенный URL в HTML-строку. Добавить регрессионные тесты импорта/рендеринга с кавычками, event-handler payloads, malformed JSON и запрещёнными схемами. Проводить проверку без выполнения payload в обычном приложении.

### P3 — Неограниченно дорогой поиск связанных задач в backup

**Где:** `src/db/backupValidation.ts:25–26, 137–148`, вызов из `src/pages/Settings.tsx:217–251`.

Для каждой строки с `taskId` валидатор вызывает `rows.tasks.find(...)`. При нескольких тысячах задач и многих связанных строках число сравнений растёт как `количество задач × количество ссылок`. Проверка синхронная и выполняется до подтверждения/транзакции импорта, поэтому специально сформированный, но укладывающийся в лимиты файл может надолго занять UI-поток. Текущие пределы — 50 MiB и 100 000 суммарных записей — ограничивают размер, но не устраняют квадратичную работу.

**Рекомендация:** построить `Map` задач по `id` один раз и проверять ссылки за O(1); при необходимости ограничить вычислительную работу и добавить крупный синтетический тест/benchmark. В аудите нагрузочный backup не создавался, продолжительность не измерялась.

### P2 — Узкий экран обрезает важные действия

**Проверено в браузере при ширине 390 CSS px.** Общая ширина страницы оставалась в пределах viewport, но внутренние группы контролов выходили за видимую область — поэтому обычный `document.scrollWidth` проблему не показывает.

- В `src/pages/ProjectWorkspace.tsx:370–445` метаданные проекта и действие запуска сессии остаются в широкой строке. Кнопка запуска начиналась примерно на x=441 px и уходила до x=571 px; селектор/приоритет также сдвинут за край. На телефоне нельзя безопасно нажать часть функций без изменения раскладки.
- В `src/pages/MyTasks.tsx:95–139` фильтры статуса и приоритета находятся в одной flex-строке. Кнопка «Низкий» начиналась около x=395 px; контейнер фильтра имел scrollWidth 429 при clientWidth 340 px, но сам не предоставлял отдельной прокрутки.

**Рекомендация:** на малых ширинах явно перестроить блоки в колонку или сделать доступную горизонтальную прокрутку фильтров с видимым affordance. Проверить 320/360/390/768 px и keyboard focus на всех фильтрах и действиях.

### P3 — Локализация активной сессии частично не переключается

**Где:** `src/components/sessions/ActiveSessionPanel.tsx:166, 196, 258–261`.

При русском интерфейсе остаются строки `Elapsed Time`, `No objective set for this session.`, `Started at` и `Banked`. Это не мешает таймеру, но визуально ломает локализованный интерфейс. Рекомендуется перенести их в используемые словари i18n и проверить обе локали на активной, паузированной и завершённой сессии.

### P3 — Доступность и семантика

- `src/components/layout/Layout.tsx:21` создаёт основной `<main>`, а `src/pages/KnowledgeHub.tsx:362` вкладывает второй `<main>`. Вложенные main landmarks некорректны для landmark-навигации. Внутренний контейнер лучше сделать `section`/`div` с подходящим label.
- `src/pages/ProjectWorkspace.tsx:355–359`: заголовок проекта — `<h1>` с `onClick`, но без button semantics, клавиатурного действия и focus indicator. Переименование через мышь работает, но для клавиатуры и скринридера не представлено как действие. Сделать отдельную именованную кнопку редактирования или доступный интерактивный control.
- Не проверялись вручную screen reader, high-contrast mode и полное управление клавиатурой. Нужен отдельный accessibility pass после исправлений.

### P3 — Умеренное предупреждение dev-зависимости

`npm audit` находит 3 advisory-записи, связанные с `postcss-selector-parser@6.1.5` в цепочке Tailwind CSS/PostCSS; production-only проверка `npm audit --omit=dev` чистая. Это build-time зависимость, и в текущем приложении не найден поток пользовательских CSS-селекторов в этот парсер. Поэтому это задача обслуживания dependency tree, а не подтверждённая уязвимость production runtime. Не применять автоматическое принудительное обновление без проверки: предложенное обновление Tailwind major может быть несовместимым. Сводка advisory: [GitHub Security Advisory GHSA-rj75-hqrm-r3gf](https://github.com/advisories/GHSA-rj75-hqrm-r3gf).

Браузерный smoke-test работал на отдельном origin `http://127.0.0.1:5191` с изолированной IndexedDB, без доступа к реальным записям пользователя. Проверены:

- создание/просмотр/удаление тестового календарного блока;
- экспорт backup, успешное уведомление и встроенная проверка целостности (`Нарушенных связей не найдено.`);

Сценарии демонстрируют, что ключевые маршруты и основные операции связаны корректно в проверенной сборке. Они **не** доказывают отсутствие ошибок во всех состояниях: не выполнялись все возможные комбинации фильтров, все формы/валидации, crash recovery при реальном падении браузера, работа с повреждённой БД, синхронизация между вкладками (серверной синхронизации нет), все размеры экранов и все типы backup.

## Ограничения и итог

- Это аудит текущей локальной копии, а не production-развёртывания; HTTP headers, CSP, TLS, обновления/синхронизацию и серверные политики проверить нельзя.
- Основные страницы и типовые сквозные потоки прошли, но покрытие не исчерпывает каждую кнопку и каждую ветку логики.
- Не проверялись восстановление после принудительного завершения браузера, конкурентная запись между реальными пользовательскими вкладками, импорт атакующего backup с выполнением кода или нагрузка на файле у максимального лимита.
- Из-за уже грязного рабочего дерева не делалось сравнение с «чистой» исходной базой и не приписывались текущие изменения автору аудита.
- Исправления не вносились; существующие несохранённые изменения и данные не сбрасывались. Новым артефактом аудита является только этот файл.

**Рекомендуемый порядок последующей работы:** (1) закрыть XSS через контекстно-безопасный рендеринг ссылок и строгую проверку rich-text backup; (2) устранить мобильное обрезание контролов; (3) сделать lookup связей backup линейным; (4) закрыть локализацию, доступность и lint warnings; (5) обновить dev dependency после проверки совместимости.

## Дополнение после аудита — 26 октября 2026 г.

**Статус P2 XSS: исправлено.** В общем конвертере inline-разметки текст и значение `href` теперь экранируются для HTML-контекста до передачи во все места `dangerouslySetInnerHTML`. Проверка URL дополнительно обнаруживает `javascript:`, `data:` и `vbscript:` после удаления управляющих ASCII-символов, которые браузер может игнорировать. Существующие другие схемы ссылок сохранены ради совместимости; `http`, `https`, `mailto` и относительные URL продолжают проходить проверки.

Изменены `src/components/knowledge/editor/editorTypes.ts`, `src/components/knowledge/editor/NoteEditor.tsx` и `src/components/knowledge/editor/editor.test.ts`. Добавлена регрессия с кавычкой и `onmouseover` в `href`, проверки обхода `javascript:` переводом строки/табуляцией/CR/NUL и контроль сохранения существующей схемы `ftp:`. Новый тест сначала падал на исходной реализации, затем прошёл после исправления. Браузерный HTML parser подтвердил, что сериализованная ссылка содержит только `href`, `target` и `rel`, а `onmouseover` отсутствует; обработчик не запускался.

После исправления прошли: полный Vitest (27 файлов; 330 passed, 1 skipped), `npm run build` (включая `tsc -b`), `npm run lint` (0 ошибок; прежние 12 предупреждений остаются) и `npm run check:bundle`. Остальные находки этого аудита не исправлялись.
